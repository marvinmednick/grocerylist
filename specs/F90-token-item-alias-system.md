## Feature: Token & Item Alias System — Phase A

### Context

F90 adds a two-level alias system: **token aliases** (word-level, composable — "chk" → "chicken") and **item aliases** (product-level — "Chicken Tenders" as an alias for "Chicken Breast Strips"). Both integrate into the F44 parser pipeline so shorthand input produces the same structured results as fully-typed input.

Phase A covers: database schema, migrations, RLS, seed script, React Query hooks, parser expansion step, `ParsedInput` extensions, and `SmartAddItem` integration. Phase B (UI — abbreviations screen, item edit modal sections, avatar menu entry) will be a separate spec.

Design decisions recorded in `docs/design/F90-token-item-alias-system.md`.

### Database / Schema Changes

#### Migration: `supabase/migrations/20250101000016_f90_alias_system.sql`

```sql
-- 1. word_aliases table (household-scoped)
CREATE TABLE word_aliases (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  household_id UUID NOT NULL REFERENCES households(id) ON DELETE CASCADE,
  alias TEXT NOT NULL,
  canonical TEXT NOT NULL,
  created_by UUID REFERENCES profiles(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE UNIQUE INDEX word_aliases_hh_alias_unique
  ON word_aliases (household_id, LOWER(alias));
CREATE INDEX word_aliases_household_idx ON word_aliases(household_id);

ALTER TABLE word_aliases ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Users can access their household's word aliases"
  ON word_aliases FOR ALL
  USING (household_id = get_my_household_id());

-- 2. abbreviation_suggestions table (global, read-only for clients)
CREATE TABLE abbreviation_suggestions (
  word TEXT NOT NULL,
  suggestion TEXT NOT NULL,
  PRIMARY KEY (word, suggestion)
);

-- No RLS — globally readable via anon key, admin-writable only
-- Grant read access for authenticated users
ALTER TABLE abbreviation_suggestions ENABLE ROW LEVEL SECURITY;
CREATE POLICY "Anyone can read abbreviation suggestions"
  ON abbreviation_suggestions FOR SELECT
  USING (true);

-- 3. items.aliases column
ALTER TABLE items ADD COLUMN aliases TEXT[] NOT NULL DEFAULT '{}';

-- 4. list_items.match_metadata column
ALTER TABLE list_items ADD COLUMN match_metadata JSONB;
```

### Parser Changes — Detailed

#### 1. Extend `MasterItemRef` (parser.ts:64)

```typescript
export interface MasterItemRef {
  id: string;
  name: string;
  default_qty: string | null;
  alternate_qtys: string[] | null;
  aliases: string[];  // NEW — item-level alternate names
}
```

Also update the duplicate in `api/items.ts:31` to match. (Both must stay in sync until the backlog item to deduplicate is addressed.)

#### 2. Extend `ParsedInput` (parser.ts:46)

```typescript
export interface ParsedInput {
  name: string;              // display name — alias if matched via alias, canonical otherwise
  canonicalName: string;     // always the master item's real name
  matchedItemId: string | null;
  matchedVia: 'name' | 'alias';  // how the match occurred
  count: number | null;
  packageType: string | null;
  packagePlural: string | null;
  sizeDescriptive: string | null;
  sizeQty: number | null;
  sizeUnit: string | null;
  storeHint: string | null;
  orphans: string[];
}
```

When `matchedVia === 'name'`: `name === canonicalName`.
When `matchedVia === 'alias'`: `name` is the alias that matched, `canonicalName` is the master item's real name.
When `matchedItemId === null` (one-off / unmatched): set `canonicalName` equal to `name` and `matchedVia: 'name'`.

#### 3. New function `expandAliases`

```typescript
export function expandAliases(
  candidate: CandidateFields,
  wordAliases: Map<string, string>
): CandidateFields[] {
```

Algorithm:
1. For each word in `candidate.nameWords`, check if `wordAliases.has(word.toLowerCase())`
2. Build the cartesian product: for each expandable word, produce variants with the original word and the expanded form
3. Return all variants as `CandidateFields[]` (each variant is a shallow copy of `candidate` with a different `nameWords` array)
4. If no words have aliases, return `[candidate]` (the original, unmodified)

With N expandable tokens, this produces 2^N variants. For typical grocery input (2–4 name tokens), that's 4–16 variants — acceptable.

#### 4. Extend `resolveNames` (parser.ts:466)

Current signature:
```typescript
export function resolveNames(candidate: CandidateFields, masterItems: MasterItemRef[]): ParsedInput[]
```

Changes:
- For each `masterItems` entry, iterate the canonical name AND each alias as separate lookup targets
- Track which name was matched (canonical vs. alias) for each result
- Set `canonicalName` to `item.name` (always the real name)
- Set `name` to the alias string when matched via alias, or `item.name` when matched via canonical name
- Set `matchedVia` accordingly
- When the same item is matched with equal token coverage via both canonical name and alias, prefer the canonical name match (deterministic output)

Implementation approach — build a flattened lookup array before the iteration:

```typescript
interface LookupEntry {
  id: string;
  lookupName: string;       // the name to match against (canonical or alias)
  canonicalName: string;    // always the master item's real name
  matchedVia: 'name' | 'alias';
  default_qty: string | null;
  alternate_qtys: string[] | null;
}
```

Flatten each `MasterItemRef` into 1 + N entries (1 for canonical name, N for aliases). Then iterate `lookupEntries` instead of `masterItems` in the existing loop.

The dedup logic (existing `Map<string, ParsedInput>` at line 521) already dedupes by `matchedItemId`. When the same item is found via both canonical and alias with same orphans, the first match wins. To ensure canonical-name preference, put canonical entries before alias entries in the flattened array.

#### 5. Update `parseInput` (parser.ts:541)

New signature:
```typescript
export function parseInput(
  input: string,
  vocabulary: Vocabulary,
  masterItems: MasterItemRef[],
  wordAliases?: Map<string, string>
): ParseResult
```

The `wordAliases` parameter is optional (defaults to empty Map) for backward compatibility with existing tests.

Updated flow:
```
tokenize → classifyTokens → groupTokens → assembleCandidate
  → expandAliases(candidate, wordAliases)    // NEW
  → for each variant: resolveNames(variant, masterItems)
  → pool all interpretations
  → dedup by matchedItemId (prefer fewest orphans, then canonical over alias)
  → sort by name token count descending
  → return ParseResult
```

#### 6. Update unmatched-item `ParsedInput` construction

Anywhere a `ParsedInput` is constructed for an unmatched item (in the parser or in SmartAddItem's prefix fallback), add the new fields:
- `canonicalName: name` (same as `name` for unmatched items)
- `matchedVia: 'name'` (default for non-alias matches)

This includes:
- The prefix fallback interpretations in SmartAddItem (line ~155)
- Any fallback construction where `matchedItemId` is null

#### 7. Update SmartAddItem prefix fallback

The `prefixFallbackInterpretations` memo needs two changes:
1. **Token alias expansion on name tokens:** Before prefix matching, expand each name token that has an alias. Include both original and expanded forms in the matching. A master item matches if every name token (or its expansion) is a prefix of at least one item word.
2. **Match against item aliases too:** When filtering `masterItemNames`, check both `item.name` and each entry in `item.aliases`. If matched via alias, set `name` to the alias, `canonicalName` to `item.name`, `matchedVia: 'alias'`.
