## Feature: Multi-User Trip Management

### Context

The shopping list is shared across a household. Multiple people may shop at the same time — together at one store, or independently at different stores. This feature makes check-offs visually attributed to the person who did them, enables each user to end only their own trip when shopping simultaneously, and auto-assigns each new user a distinct profile color at signup. It builds on the trip history screen (F9, Done) and the Settings screen (F7, Done).

Addresses the following user scenarios:
- **Shopping together:** Both users check off items; each wants to see whose is whose
- **Shopping separately:** Each user ends their own trip without affecting the other's active items
- **At a glance:** Who got the milk?

### Supabase Query Shapes

**`useHouseholdMembers` query (new, in `api/profile.ts`):**
```typescript
supabase
  .from('profiles')
  .select('id, display_name, display_name_short, color')
  .eq('household_id', householdId!)
```
React Query key: `['household_members', householdId]`
`staleTime: 5 * 60 * 1000` (5 minutes — profiles change rarely)

**`useShoppingList` query (existing, in `api/list.ts`):**
No join change needed. `purchased_by` is a scalar column on `list_items` and will be included in the existing `*` select automatically. Update the `ListItem` TypeScript interface to include it.

**`useTogglePurchased` mutation update (in `api/list.ts`):**
```typescript
supabase
  .from('list_items')
  .update({
    is_purchased,
    purchased_at: is_purchased ? new Date().toISOString() : null,
    purchased_by: is_purchased ? userId : null,   // userId from useHousehold()
  })
  .eq('id', id)
  .select()
  .single()
```
`userId` is captured at hook initialization from `useHousehold().userId` (not called inside `mutationFn`).

**`useEndTrip` mutation update (in `api/list.ts`):**

New signature: `{ store_id?: string; user_id?: string }`

```typescript
// Trip record: use user_id param if provided (multi-user path), else fall back to current user
user_id: targetUserId ?? currentAuthUser?.id ?? null

// Archival query — add user_id filter only when provided (multi-user path)
let query = supabase
  .from('list_items')
  .update({ archived_at: new Date().toISOString(), trip_id: trip.id })
  .eq('is_purchased', true)
  .is('archived_at', null);

if (store_id) query = query.eq('store_id', store_id);
if (targetUserId) query = query.eq('purchased_by', targetUserId);
```

When `targetUserId` is omitted (single-user path), all purchased items at the store are archived — existing behavior unchanged. When `targetUserId` is provided (multi-user path), only that user's items are archived.

### Undo/Redo Registration

**`useTogglePurchased` — existing `pushAction` call in `index.tsx`:**
No change to undo label or logic. Undo/redo already registered in `handleToggle`. The `purchased_by` field is implicitly reverted because undo calls `togglePurchased` with the opposite `is_purchased` value, which clears/sets `purchased_by` accordingly.

**Single-user end trip (`handleEndTrip` — existing path):**
No change. `pushAction` is already registered with `revertArchival` undo.

**Multi-user end trip (new `handleEndSelectedTrips` in `index.tsx`):**
Called when the user taps "End Selected Trips" in `MultiTripModal`.

```
label: "Ended N trips at [StoreName]"   (e.g. "Ended 2 trips at Costco")
       or "Ended N trips" for global end-all

undo:  call revertArchival({ trip_id }) for each created trip ID (Promise.all)
redo:  call endTrip({ store_id, user_id }) for each originally-selected user (Promise.all)
```

Use `mutateAsync` (not `mutate`) for all `endTrip` and `revertArchival` calls that contribute to a shared `pushAction`.

### `lib/household.tsx` — Adding `userId`

Add `userId: string | null` to `HouseholdContextType` and expose it from the query:

```typescript
interface HouseholdContextType {
  householdId: string | null;
  userId: string | null;            // NEW
  displayName: string | null;
  displayNameShort: string | null;
  avatarColor: string | null;
  isLoading: boolean;
}
```

In the query function, the `session.user.id` is already available at the point where the profile is fetched. Return it alongside the profile data by storing it in the provider's value:

```typescript
const { data: profileData, isLoading } = useQuery({
  queryKey: ['my_profile'],
  queryFn: async () => {
    const { data: { session } } = await supabase.auth.getSession();
    if (!session) return null;
    const { data, error } = await supabase
      .from('profiles')
      .select('household_id, display_name, display_name_short, color')
      .eq('id', session.user.id)
      .single();
    if (error) throw error;
    return { ...data, userId: session.user.id };  // attach userId to result
  },
  staleTime: Infinity,
});

// In the Provider value:
value={{
  householdId: profileData?.household_id ?? null,
  userId: profileData?.userId ?? null,            // NEW
  displayName: profileData?.display_name ?? null,
  displayNameShort: profileData?.display_name_short ?? null,
  avatarColor: profileData?.color ?? null,
  isLoading,
}}
```

Add a palette constant and a helper. Place the constant at the module level (above `AuthScreen`):

```typescript
const PROFILE_COLOR_PALETTE = [
  '#2563eb', // blue-600
  '#16a34a', // green-600
  '#ea580c', // orange-600
  '#9333ea', // purple-600
  '#dc2626', // red-600
  '#0d9488', // teal-600
  '#db2777', // pink-600

```

Export a standalone async helper for testability (also call it from `ensureProfile`):

```typescript
export async function pickProfileColor(householdId: string): Promise<string> {
  const { data: existing } = await supabase
    .from('profiles')
    .select('color')
    .eq('household_id', householdId);
  const usedColors = new Set((existing ?? []).map(p => p.color).filter(Boolean));
  return PROFILE_COLOR_PALETTE.find(c => !usedColors.has(c)) ?? PROFILE_COLOR_PALETTE[0];
}
```

In `ensureProfile`, call `pickProfileColor(hh.id)` before the insert and include `color` in both branches (single and multi household mode):

```typescript

await supabase.from('profiles').insert({
  id: userId,
  household_id: hh.id,
  display_name: email,
  color,
```

### `app/(tabs)/index.tsx` — End Trip Multi-User Logic

**`handleEndTrip(storeId?, storeName?)` updated logic:**

```
1. Filter listItems for: is_purchased === true AND store_id matches (if storeId provided)
2. Collect distinct purchased_by values (excluding null)
3. If 0 distinct purchasers: nothing to do (no-op — button shouldn't be visible anyway)
4. If 1 distinct purchaser (or only null purchased_by items):
   → Show Alert confirmation (existing behavior)
   → On confirm: call endTrip({ store_id: storeId })
   → Register pushAction (existing behavior)
5. If 2+ distinct purchasers:
   → Build TripUser[] by cross-referencing purchased_by UUIDs with memberMap
   → Set multiTripContext = { storeId, storeName, users: TripUser[] }
   → Set isMultiTripModalVisible = true
   → (No Alert shown — modal replaces it)
```

**`handleEndSelectedTrips(selectedUserIds: string[])` — new handler:**

Called by `MultiTripModal.onConfirm`. Runs in three steps:

```typescript
// 1. End a trip per selected user
const results = await Promise.all(
  selectedUserIds.map(userId =>
    endTrip({ store_id: multiTripContext.storeId === 'other' ? undefined : multiTripContext.storeId, user_id: userId })
  )
);

// 2. Collect trip IDs for undo
const tripIds = results.filter(r => r?.trip?.id).map(r => r.trip.id);

// 3. Single pushAction covering all
pushAction({
  label: `Ended ${selectedUserIds.length} trips at ${multiTripContext.storeName || 'all stores'}`,
  undo: async () => {
    await Promise.all(tripIds.map(tripId => revertArchival({ trip_id: tripId })));
  },
  redo: async () => {
    await Promise.all(
      selectedUserIds.map(userId =>
        endTrip({ store_id: multiTripContext.storeId === 'other' ? undefined : multiTripContext.storeId, user_id: userId })
      )
    );
  },
});

// 4. Close modal
setIsMultiTripModalVisible(false);
setMultiTripContext(null);
```

New state variables:
```typescript
const [isMultiTripModalVisible, setIsMultiTripModalVisible] = useState(false);
const [multiTripContext, setMultiTripContext] = useState<{
  storeId?: string;
  storeName?: string;
  users: TripUser[];
} | null>(null);
```

Render `<MultiTripModal>` near the bottom of the component's JSX (alongside the existing edit modal):
```tsx
<MultiTripModal
  visible={isMultiTripModalVisible}
  storeName={multiTripContext?.storeName ?? 'All Stores'}
  users={multiTripContext?.users ?? []}
  onConfirm={handleEndSelectedTrips}
  onCancel={() => { setIsMultiTripModalVisible(false); setMultiTripContext(null); }}
/>
```

### Acceptance Criteria

- [ ] When a user checks off an item, `purchased_by` is set to their user ID on the `list_items` row
- [ ] When a user unchecks an item, `purchased_by` is cleared to `null`
- [ ] On the shopping list, items checked off by the current user render an outlined circle with a checkmark in the user's profile color
- [ ] On the shopping list, items checked off by another household member render a filled circle in that member's profile color with a white checkmark
- [ ] Unchecked items render a gray circle (unchanged)
- [ ] Items with `purchased_by = null` (legacy rows) render as the current user's outlined style
- [ ] A newly created profile is auto-assigned the first unused color from the 7-color palette
- [ ] If all 7 palette colors are in use, the assignment cycles back to blue (`#2563eb`)
- [ ] When a single user has purchased items at a store, "End Trip" shows the existing Alert confirmation and creates one trip record (unchanged behavior)
- [ ] When multiple users have purchased items at a store, "End Trip" shows the multi-user selection modal instead of the Alert
- [ ] The multi-user modal lists each purchaser's name, initials badge (in their color), and item count
- [ ] All users are selected by default in the modal
- [ ] Deselecting a user in the modal leaves their purchased items active after tapping "End Selected Trips"
- [ ] "End Selected Trips" creates one `shopping_trips` record per selected user, archiving only that user's purchased items
- [ ] Undo after a multi-user end trip reverts all archived records and deletes all created trip records in a single undo action
- [ ] The global "End All Shopping Trips" footer button also uses the multi-user detection logic when multiple purchasers are present across all stores
- [ ] The "End Selected Trips" button is disabled when no users are selected in the modal
