## Feature: List Item / Quantity Model Refactor

### Context

Split `list_items` into a parent row (per-item fields) and a new child `list_item_quantities` table (per-quantity fields). A single logical list item can then hold one or more quantity entries. This is a pure refactor — **no user-visible behavior change**. Every existing `list_items` row migrates to a single-entry parent; every rendered row looks and behaves as before. Multi-entry items only appear once F78 (which consumes this refactor) ships.

Design decisions recorded in `docs/design/F103-list-item-quantity-refactor.md`. Read it before starting — it covers the rationale for every non-obvious choice (JSONB vs child table, Option B query shape, parent `archived_at` bookkeeping, deferral of the unique index to F78, realtime name-lookup, migration strategy).

### Database / Schema Changes

**New migration file:** `supabase/migrations/20250101000019_f103_list_item_quantities.sql`

The migration performs, in order (all in a single transaction):

#### 1. Create the new table

```sql
CREATE TABLE list_item_quantities (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    list_item_id UUID NOT NULL REFERENCES list_items(id) ON DELETE CASCADE,
    quantity TEXT,
    quantity_parsed JSONB NULL,
    is_purchased BOOLEAN DEFAULT FALSE,
    purchased_at TIMESTAMPTZ,
    purchased_by UUID,
    trip_id UUID REFERENCES shopping_trips(id) ON DELETE SET NULL,
    archived_at TIMESTAMPTZ,
    added_at TIMESTAMPTZ DEFAULT NOW(),
    added_by UUID,
    household_id UUID NOT NULL REFERENCES households(id) ON DELETE CASCADE,
    created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX list_item_quantities_list_item_idx ON list_item_quantities(list_item_id);
CREATE INDEX list_item_quantities_household_idx ON list_item_quantities(household_id);
CREATE INDEX list_item_quantities_active_idx ON list_item_quantities(archived_at) WHERE archived_at IS NULL;
```

#### 2. Enable RLS + realtime

```sql
ALTER TABLE list_item_quantities ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Household members can manage list_item_quantities" ON list_item_quantities
    FOR ALL TO authenticated
    USING (household_id = get_my_household_id())
    WITH CHECK (household_id = get_my_household_id());

ALTER PUBLICATION supabase_realtime ADD TABLE list_item_quantities;
```

#### 3. Dedup sweep — merge duplicate parents

For each `(item_id, store_id, household_id)` group in `list_items` where `archived_at IS NULL AND item_id IS NOT NULL` with more than one row:
- Pick the earliest-`added_at` row as **keeper**.
- Insert a `list_item_quantities` entry for each row in the group (including the keeper), carrying its per-quantity fields.
- Delete the non-keeper `list_items` rows.

```sql
-- Insert entries for active master-item rows that are part of a duplicate group
INSERT INTO list_item_quantities (
    list_item_id, quantity, quantity_parsed, is_purchased, purchased_at, purchased_by,
    trip_id, archived_at, added_at, added_by, household_id
)
SELECT
    keeper.id,
    dup.quantity, dup.quantity_parsed, dup.is_purchased, dup.purchased_at, dup.purchased_by,
    dup.trip_id, dup.archived_at, dup.added_at, dup.added_by, dup.household_id
FROM list_items dup
JOIN LATERAL (
    SELECT id FROM list_items k
    WHERE k.item_id = dup.item_id
      AND k.store_id IS NOT DISTINCT FROM dup.store_id
      AND k.household_id = dup.household_id
      AND k.archived_at IS NULL
      AND k.item_id IS NOT NULL
    ORDER BY k.added_at ASC, k.id ASC
    LIMIT 1
) keeper ON TRUE
WHERE dup.archived_at IS NULL
  AND dup.item_id IS NOT NULL
  AND EXISTS (
    SELECT 1 FROM list_items sibling
    WHERE sibling.item_id = dup.item_id
      AND sibling.store_id IS NOT DISTINCT FROM dup.store_id
      AND sibling.household_id = dup.household_id
      AND sibling.archived_at IS NULL
      AND sibling.item_id IS NOT NULL
      AND sibling.id <> dup.id
  );

-- Delete non-keeper duplicates
DELETE FROM list_items
WHERE id IN (
    SELECT dup.id FROM list_items dup
    JOIN LATERAL (
        SELECT id FROM list_items k
        WHERE k.item_id = dup.item_id
          AND k.store_id IS NOT DISTINCT FROM dup.store_id
          AND k.household_id = dup.household_id
          AND k.archived_at IS NULL
          AND k.item_id IS NOT NULL
        ORDER BY k.added_at ASC, k.id ASC
        LIMIT 1
    ) keeper ON TRUE
    WHERE dup.archived_at IS NULL
      AND dup.item_id IS NOT NULL
      AND dup.id <> keeper.id
);
```

**Scope note:** dedup only applies to master items (`item_id IS NOT NULL`) and active rows (`archived_at IS NULL`). One-offs and archived rows are not deduped.

#### 4. Split — create a single entry for every remaining row

```sql
INSERT INTO list_item_quantities (
    list_item_id, quantity, quantity_parsed, is_purchased, purchased_at, purchased_by,
    trip_id, archived_at, added_at, added_by, household_id
)
SELECT
    id, quantity, quantity_parsed, is_purchased, purchased_at, purchased_by,
    trip_id, archived_at, added_at, added_by, household_id
FROM list_items;
```

(After dedup, every `list_items` row — active or archived — gets exactly one entry carrying its per-quantity fields.)

#### 5. Drop per-quantity columns from `list_items`

```sql
ALTER TABLE list_items
    DROP COLUMN quantity,
    DROP COLUMN quantity_parsed,
    DROP COLUMN is_purchased,
    DROP COLUMN purchased_at,
    DROP COLUMN purchased_by,
    DROP COLUMN trip_id;
```

**Keep** on `list_items`: `id`, `item_id`, `name`, `category_id`, `store_id`, `warnings`, `match_metadata`, `added_at`, `added_by`, `household_id`, `archived_at`, `created_at`.

#### 6. Update `supabase/full_schema.sql`

Reflect the new `list_items` shape and add the `list_item_quantities` table, RLS policy, realtime publication, and indexes.

**No unique index** on `list_items(item_id, store_id, household_id)` — that lands with F78.

**`useAddToList` — insert parent + first entry:**

The `ListItemInsert` shape stays the same (caller doesn't need to know about the split). The mutation performs two sequential inserts:

1. Insert into `list_items` (per-item fields: `name`, `item_id`, `store_id`, `category_id`, `warnings`, `match_metadata`, `added_by`, `household_id`). Capture returned `id` as `listItemId`.
2. Insert into `list_item_quantities` (`list_item_id: listItemId`, `quantity`, `quantity_parsed`, `added_by`, `household_id`).

If step 2 fails, delete the orphan parent from step 1 (`supabase.from('list_items').delete().eq('id', listItemId)`), then throw. This keeps the two-table insert effectively atomic for the caller.

Return value shape: `{ parent: <list_items row>, entry: <list_item_quantities row> }`. Callers that previously used the returned `id` (e.g., delete-undo's `addItem({...}).id`) need updating — see `app/(tabs)/index.tsx` changes below.

Household guard + mutation tracking apply as today.

**`useDeleteListItem` — delete entry; delete parent if last active entry:**

```typescript
mutationFn: async ({ entryId }: { entryId: string }) => {
  incrementLocalMutation();
  try {
    // Find the parent and check sibling count
    const { data: entry, error: fetchErr } = await supabase
      .from('list_item_quantities')
      .select('list_item_id')
      .eq('id', entryId)
      .single();
    if (fetchErr) throw fetchErr;

    const listItemId = entry.list_item_id;

    // Count other non-archived entries on this parent
    const { count, error: countErr } = await supabase
      .from('list_item_quantities')
      .select('*', { count: 'exact', head: true })
      .eq('list_item_id', listItemId)
      .is('archived_at', null)
      .neq('id', entryId);
    if (countErr) throw countErr;

    // Delete the entry
    const { error: delErr } = await supabase.from('list_item_quantities').delete().eq('id', entryId);
    if (delErr) throw delErr;

    // If no other active entries remain, delete the parent too
    if ((count ?? 0) === 0) {
      const { error: parentErr } = await supabase.from('list_items').delete().eq('id', listItemId);
      if (parentErr) throw parentErr;
    }

    return { entryId, listItemId, parentDeleted: (count ?? 0) === 0 };
  } finally {
    decrementLocalMutation();
  }
}
```

Caller signature changes from `(id: string)` to `({ entryId: string })`. Update `app/(tabs)/index.tsx` accordingly.

**`useEndTrip` — archive entries; archive parents whose entries are now all archived:**

```typescript
mutationFn: async ({ store_id, user_id: targetUserId }) => {
  if (!householdId) throw new Error('No household ID found');
  const { data: { user: currentAuthUser } } = await supabase.auth.getUser();
  incrementLocalMutation();
  try {
    // 1. Create trip row
    const { data: trip, error: tripError } = await supabase
      .from('shopping_trips')
      .insert({ primary_store_id: store_id || null, status: 'completed', ended_at: new Date().toISOString(), household_id: householdId, user_id: targetUserId ?? currentAuthUser?.id ?? null })
      .select().single();
    if (tripError) throw tripError;

    // 2. Archive matching entries
    // Must filter by parent.store_id — entries don't hold store_id themselves.
    // Approach: fetch parent IDs matching store scope, then archive entries by list_item_id.
    let parentIdsQuery = supabase.from('list_items').select('id').is('archived_at', null);
    if (store_id) parentIdsQuery = parentIdsQuery.eq('store_id', store_id);
    const { data: parentIds, error: parentErr } = await parentIdsQuery;
    if (parentErr) throw parentErr;
    const parentIdList = (parentIds ?? []).map(p => p.id);

    let entriesUpdate = supabase
      .from('list_item_quantities')
      .update({ archived_at: new Date().toISOString(), trip_id: trip.id })
      .eq('is_purchased', true)
      .is('archived_at', null);
    if (parentIdList.length > 0) {
      entriesUpdate = entriesUpdate.in('list_item_id', parentIdList);
    } else if (store_id) {
      // No matching parents → no-op update, still return empty items array
      return { trip, items: [] };
    }
    if (targetUserId) entriesUpdate = entriesUpdate.eq('purchased_by', targetUserId);
    const { data: archivedEntries, error: entriesError } = await entriesUpdate.select();
    if (entriesError) throw entriesError;

    // 3. Archive parents whose entries are now all archived
    // One UPDATE with a NOT EXISTS subquery:
    const { error: parentArchiveErr } = await supabase.rpc('archive_empty_list_items');
    // Alternative if RPC isn't available: do it client-side —
    //   fetch parents with their entries, find those with zero active entries,
    //   UPDATE archived_at on those parents.
    // Implementor: prefer the RPC approach; add a migration defining:
    //   CREATE FUNCTION archive_empty_list_items() RETURNS void AS $$
    //     UPDATE list_items SET archived_at = NOW()
    //     WHERE archived_at IS NULL
    //       AND NOT EXISTS (
    //         SELECT 1 FROM list_item_quantities q
    //         WHERE q.list_item_id = list_items.id AND q.archived_at IS NULL
    //       );
    //   $$ LANGUAGE sql SECURITY DEFINER;
    // (Include this function in the same 20250101000019 migration file.)
    if (parentArchiveErr) throw parentArchiveErr;

    return { trip, items: archivedEntries };
  } finally {
    decrementLocalMutation();
  }
}
```

**Add an SQL function** `archive_empty_list_items()` to the same migration file (see inline comment). It uses `SECURITY DEFINER` so the RLS predicate doesn't block the sweep.

**`useRevertArchival` — clear both tables:**

```typescript
mutationFn: async ({ trip_id }) => {
  incrementLocalMutation();
  try {
    // 1. Find entries that were archived into this trip
    const { data: entries, error: fetchErr } = await supabase
      .from('list_item_quantities').select('list_item_id').eq('trip_id', trip_id);
```

**`openEditModal(parent, entry)`:**
- Modal now takes both. Name/store fields come from `parent`; quantity comes from `entry`.

**`handleSaveEdit`:**
- Split into two mutations:
  - `useUpdateListItemFields({ id: parent.id, name, store_id, category_id })` if any parent fields changed
  - `useUpdateQuantityEntry({ id: entry.id, quantity })` if the quantity changed
- Capture snapshot of both before the calls for undo. Undo restores both.
- If only one side changed, only fire that mutation — avoid no-op UPDATEs.

**`handleDelete`:**
- Calls `deleteItem({ entryId: entry.id })`.
- Undo: restore the entry. If the parent was deleted too (indicated by `parentDeleted: true` in the return value), also re-insert the parent before the entry. Use the `addItem` path which already handles both.
- Tracker pattern: delete-undo creates new rows with new IDs; tracker carries `{ entryId, listItemId }` so redo targets the current IDs.

**`onDragEnd`:**
- The dragged row's data is `{ parent, entry }`.
- Compute target store from the nearest header upward.
- Call `useUpdateListItemFields({ id: parent.id, store_id: newStoreId })`.
- Undo snapshots `parent.store_id` (not `entry.store_id` — entries don't have store_id).
- All sibling entries follow on refetch; no per-entry mutation needed.

**`renderCheckbox(entry, parent)`:**
- Uses `entry.is_purchased` and `entry.purchased_by` (was `listItem.is_purchased` / `listItem.purchased_by`).
- Otherwise identical.

**End-trip handlers (`handleEndTrip`, `handleEndSelectedTrips`):**
- The per-store "has purchased" check now walks `listItems.flatMap(p => p.quantities).filter(...)` rather than `listItems.filter(i => i.is_purchased)`.
- `purchaserCounts` map builds from entries, not list items.
- `scopedPurchasedItems` filter now walks entries and checks each entry's `is_purchased`, `archived_at`, and parent's `store_id`.

**Row rendering:**
- Strikethrough + secondary text driven by `entry` fields where appropriate. `parent.name`, `parent.store`, `parent.category` still drive display name, store name, category.

### Undo/Redo Registration

| Action | Label | Undo | Redo |
|---|---|---|---|
| Toggle entry purchased | `${newStatus ? 'Checked' : 'Unchecked'} ${parent.name}` | `togglePurchased({ id: entry.id, is_purchased: !newStatus, purchased_by_override: originalPurchasedBy })` | `togglePurchased({ id: entry.id, is_purchased: newStatus })` |
| Edit parent fields (name/store/category) | `Edited ${parent.name}` | `updateListItemFields({ id: parent.id, ...parentSnapshot })` | `updateListItemFields({ id: parent.id, ...parentUpdates })` |
| Edit entry quantity | `Edited ${parent.name} quantity` | `updateQuantityEntry({ id: entry.id, quantity: prevQty })` | `updateQuantityEntry({ id: entry.id, quantity: newQty })` |
| Delete entry (+ maybe parent) | `Deleted ${parent.name}` | Re-add via `addItem({...})`; update tracker IDs | `deleteItem({ entryId: tracker.entryId })` |
| Drag parent to new store | `Moved ${parent.name} to ${newStoreName}` | `updateListItemFields({ id: parent.id, store_id: originalStoreId })` | `updateListItemFields({ id: parent.id, store_id: newStoreId })` |
| End trip | `Ended trip ${storeName || 'All'}` | `revertArchival({ trip_id: tripTracker.currentId })` | `endTrip(...)`, update tripTracker |

All snapshot-before-mutation per CODING.md §3 Failure Mode B. All re-create actions use tracker pattern per Failure Mode A.

When edit modal saves both parent fields and entry quantity, push **one** `pushAction` with combined undo: calls both inverse mutations in order (parent first, then entry). Do not push two separate actions for one user save.

### Household Scoping

New inserts on `list_item_quantities` must:
- Include `household_id: householdId`
- Throw `'No household ID found'` early if `householdId` is null (CODING.md §2)

Affected mutation: `useAddToList` (entry insert in the second step).

All `list_items` writes already have the guard (existing behavior).

### Realtime Mutation Tracking

Every mutation that writes to **either** `list_items` **or** `list_item_quantities` must wrap the Supabase call with `incrementLocalMutation` / `decrementLocalMutation` (CODING.md §1). This includes:
- `useAddToList` — wrap both inserts in a single increment/decrement pair (increment at top, decrement in outer finally).
- `useTogglePurchased`, `useUpdateQuantityEntry`, `useUpdateListItemFields`, `useDeleteListItem`, `useEndTrip`, `useRevertArchival` — wrap the whole mutation body.

### Acceptance Criteria

**Data model:**
- `list_items` table no longer has `quantity`, `quantity_parsed`, `is_purchased`, `purchased_at`, `purchased_by`, `trip_id` columns.
- `list_item_quantities` table exists with the shape specified, RLS enabled, realtime enabled, and three indexes.
- SQL function `archive_empty_list_items()` exists and is SECURITY DEFINER.
- Migration is idempotent-safe only if re-run from clean state; it is intended to run exactly once against existing data.

**Migration data correctness:**
- Every pre-migration `list_items` row has exactly one matching `list_item_quantities` row carrying its per-quantity fields (after dedup).
- Pre-migration duplicate `(item_id, store_id, household_id)` groups of active master-item rows collapse to one parent with N entries (one per original row).
- One-offs (`item_id IS NULL`) and archived rows are not deduped.

**Behavior (rendered UX identical to pre-F103):**
- Adding an item creates one parent + one entry; the item appears in the shopping list.
- Toggling the checkbox flips `is_purchased` on the entry; parent is untouched.
- Editing the quantity updates the entry; editing name/store/category updates the parent.
- Deleting a row deletes the entry; if it was the only active entry, the parent is deleted in the same mutation.
- Dragging a row to another store updates `parent.store_id`; if the parent has multiple entries, all sibling rows follow on refetch.
- End trip archives entries that match the scope; parents whose entries are all archived get `archived_at` set in the same transaction.
- Revert archival (undo end trip) clears `archived_at` and `trip_id` on entries and clears `archived_at` on the affected parents.
- Warning badge display, secondary text, check-color semantics, and multi-user identity rendering are visually unchanged.

**Realtime:**
- Subscriptions exist on both `list_items` and `list_item_quantities`.
- Remote changes on either table invalidate `['shopping_list']`.
- Self-mutation suppression continues to work (no self-toast after local mutations).
- Remote toast names the item correctly: from `payload.new.name` for `list_items` events, from `queryClient.getQueryData(['shopping_list'])` lookup by `list_item_id` for `list_item_quantities` events. Falls back to `"List updated"` when the parent is not in cache.

**Tests:** all 570+ pre-existing tests plus new F103 tests pass.
